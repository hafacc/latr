# latr

Monorepo with a Kotlin Android app (`android/`), shared Firestore rules (`firebase/`), and a Next.js web client (`web/`). User-facing docs live in [README.md](./README.md); this file is for contributors and AI sessions working on the code.

## Features & Expected Behavior

Track features and behavior here. When making changes, verify existing behavior isn't broken. Add unit tests when possible.

### Todo Display
- Snoozed todos show time as "<date> at <time>" using DateUtils (render date and time independently, concatenate with " at ")
- Snooze time formatting uses abs() on time delta so past snooze times >24h ago also show date+time format
- All clock times render 24-hour (`HH:mm`, e.g. `09:00`, `20:30`) on both platforms, regardless of locale or the device's 12/24-hour setting: web `hourCycle: "h23"` (`utils/format.ts`, `formatClock` in `utils/snooze-suggest.ts`), Android `SnoozeSuggestions.formatClock` (also used by `LocalDateTimeUtil.formatSnoozeTime`) and a 24-hour Material `TimePicker`. Web's custom picker takes the time as typed 24-hour text (`parseClockInput` in `utils/calendar.ts` accepts `9`, `930`, `09:30`), not a native `<input type="time">`, which would follow the browser's locale.

### Snooze Options (learned suggestions)
- Both platforms have replaced their hand-tuned presets (the old `getSnoozeOptions`/`SnoozeTimeCalculator`, gated on time-of-day/weekday) with a menu that learns from the user's own snooze history: web `utils/snooze-suggest.ts`, Android `util/SnoozeSuggestions.kt` (Room schema v11 adds two tables, `snooze_sets` and `snooze_tod`; v12 adds `snooze_picks`) — the same pure algorithm on both platforms, no model or network call involved, just decayed counters. Both run the same cases from `testdata/snooze-fixtures.json`, covering keys, resolution, day phrase/distance/weekday/region, wire parsing and what a commit does to the other sets and quick times (finished label strings are tested per platform).
- **Pattern extraction.** Every commit `(at, target)` decomposes into "keys": a date rule (`D0`, `D1`, … relative days, any number of days out, so 8 and 9 days are their own keys rather than rounding to a week; `W1..4` relative weeks, `Wd1..7` a weekday, `Wn1..7` that weekday once more, `Dom1`/`Dom15`/`DomL` day-of-month anchors, `Mo1..3` relative months) paired with either an exact clock time rounded to 5 minutes (`D0@0900`) or an hour offset from the commit (`D0_h3`, 0-12h; days counted on the wall clock, hours as elapsed time, so DST doesn't shift it). An offset is only learned, and only resolves, when it lands on the snooze day its date rule names: an evening snooze to tomorrow morning is a clock time tomorrow, not "today + 11 hours" (that crossing offset used to outvote real same-day times and label Friday as "In 2 days"). Days use a 05:00 boundary ("snooze day"). Weekday numbers are ISO-8601 (Monday=1..Sunday=7) on **both** platforms — web's `isoDow()` converts JS's `getDay()` so weekday keys merge when synced.
- **A clock key always points to the next time that hits, never the past.** Its date rule counts from the key's *first hit*: the first time its clock time comes round at least a minute after the reference time (the commit when learning, `now` when resolving; `firstHitDay`). `D0@1300` is the next 13:00 (today's if still ahead, else tomorrow's), `D1@1300` the one after, `W1@1300` a week after the next; `Wd4@0900` is the first Thursday 09:00 from the next 09:00 on (today at 07:00 on a Thursday, a week out at 10:00), `Wn4` the Thursday after that; `Dom1`/`Dom15`/`DomL` are the first matching day from the first hit on, so the 1st counts on the 1st until its time passes. `Mo1..3` still count months from today's snooze day (they can't land in the past). Extraction (`clockRulesFor`/`extractTimedKeys`) keeps every candidate rule whose key, resolved at the commit, lands on the target's slot, so it's the exact inverse: 22:00 → tomorrow 09:00 and 08:00 → today 09:00 both teach `D0@0900` (the first also teaches tomorrow's weekday). The 05:00 boundary still decides which day a night time belongs to (so Friday 01:00 is Friday night's, for weekday/day-of-month rules and labels) and the same-day rule below. Hour offsets keep their meaning: counted from today's snooze day, `Wd` 1-7 and `Wn` 8-14 days out, so a set can hold `D0@1000` with `D1_h0` (a snooze to tomorrow at the same time).
- **Time is freeform; morning/afternoon/evening/night only name a row.** The region word comes from the time a row resolves to, never from the key. Two clock times for one date rule (tomorrow 9:00 and tomorrow 20:00) are two keys and can both show. Only rows at exactly the same time are duplicates: 9:00 and 9:05 are two rows. (A windowed-sum score was rejected: a rare 9:30 between strong 9:00 and 10:00 clusters would outscore both.)
- **Same-day snoozes only teach same-day keys.** A commit landing on the same snooze day produces only `D0@…` and `D0_h…`, never weekday or other families (even though a weekday or day-of-month key would now resolve to it).
- **No credit splitting.** The exact *set* of keys one commit matched (not the individual keys) is what gets a decayed count, incremented by a full 1.0 each time that same combination recurs. Two different combinations are two different counters.
- **Ranking is greedy aggregate-then-spend, then discount what's near the pick.** For each candidate key, sum the live (decayed) counts of every still-available set containing it; pick the highest; retire ("spend") every set containing that key, and any other key resolving to exactly the same time; then lower every remaining key's score by the winner's own (undiscounted) score × 2^(−|Δt| / 30 min), Δt between the two resolved instants (`NEARBY_HALF_DISTANCE_MINUTES`; clock keys and hour offsets alike, across days); repeat, up to 5 rows. Discounts from every pick so far add up; a discounted score floors at 0 but the key stays a candidate (it can still fill a later row when nothing better is left), since the 0.05 eligibility floor applies to the undiscounted score. So a weaker 19:00 near a strong 20:00 gives way to a distant time, and a 5-minute neighbour usually shows as its other reading (e.g. its weekday) if it has one. Equal discounted scores go to the higher undiscounted score, then the tie-break below. Only keys that resolve compete (a clock key always does; an offset that would leave its day doesn't), so after 13:00 a 13:00 habit wins as tomorrow's 13:00 and still spends the sets its "in N hours" offsets share. `liveMembers` drops what extraction can't produce (sets conversion, below, couldn't fix): a set whose clock keys disagree about the day (a `Wd` with a day count past 6, `Wn` outside 7-13, `W` not matching it) is ignored whole, and offsets whose day count isn't the clock key's or one more (saved across midnight by older builds) are dropped from their set. Scores within a relative 1e-9 count as tied (the platforms sum doubles in different orders). Tie-break: a clock time beats an hour offset first; then a day count resolving to today or tomorrow, then a key naming a specific weekday/day of month (`Wd`/`Wn`/`Dom`/`DomL`), then one counting days/weeks/months (`D` further out, `W`, `Mo`), shorter period first within each group, then code-unit key order.
- **Counts saved before the first-hit rule are converted when read.** Only the per-device blocks older builds saved carry this: a block has `v: 2`; one without it (or below 2) is old, and `fromWire` rewrites its sets (`upgradeLegacySets`): each set's clock keys are resolved the old way (date rule counted from the snooze day of the set's `t`, its last commit; `legacyClockTime`, used for nothing else), and if they agree on one target the set is re-extracted from `(t, target)`, keeping `c` and `t`. So an evening "tomorrow 08:00" set `D1@0800` becomes `D0@0800`, and an old weekly `D7`+`W1`+`Wd` set becomes `D6`+`Wd`. Sets landing on one new id merge (both decayed to the later `t`, summed); a set whose clock keys don't agree is kept as saved. Only the last commit time survives, so a set whose commits came at different times of day converts as if all were made at the last one. It runs once per block, when the block is folded into the account's shared counts (see [Firestore schema](#firestore-schema)), and for signed-out counts kept on the device (Android's Room sets once at load, marked by `snoozeSetsVersion`; web's localStorage copy is always written with `v: 2`).
- **Labels are computed from the resolved instant**, not the key's day number. Weekday rows read "This <weekday>" 1-6 days out, "Next <weekday>" 7-13 days out (so on a Thursday once its time has passed, the coming Thursday is "Next Thursday"), "<weekday> in 2 weeks" at 14. Day and week rows (`D`/`W`) past tomorrow name the weekday the same way under 14 days ("In 2 days" on a Wednesday reads "This Friday"), and only count ("In 2 weeks") from 14 on; the keys themselves are unchanged. Same-day clock rows read "This morning" / "This afternoon" / "This evening" / "Tonight", except day-of-month and month rows, which keep their calendar phrase ("The 1st" later on the 1st). Same-day hour offsets read "In a little while (<time>)" up to 3 hours and "Much later (<time>)" beyond; the time tells same-phrase rows apart.
- **A snooze takes votes from nearby times.** Decay alone was too slow to follow a moved habit: with 20:00 at ~29 votes and 19:00 at ~16, it took about 12 more daily 19:00 snoozes before 19:00 led. So after a commit credits its own set, every *other* set in the account's counts (signed out: the device's own) loses share × its count, as last seen by the committing device. share is the largest 2^(−|Δ| / 30 min) among the set's clock keys, each resolved at the commit time with the normal resolver, Δ from that instant to the target's 5-minute slot: 0.25 an hour away, 0.5 at 30 minutes, ~0.89 at 5 (the same `NEARBY_HALF_DISTANCE_MINUTES` as the menu discount, which is unchanged). Distance is between instants, so at 21:00 the next 20:00 is tomorrow's and a snooze to tomorrow 19:00 is an hour from it, while the same clock time a day off loses practically nothing. Untouched: the credited set, any set with a clock key landing exactly on the target's slot, and sets with only hour offsets. It runs on every commit, whatever the source or picked row, with no exceptions and, by choice, no protection for recently used times (a "not snoozed to in 7 days" guard was simulated and dropped as needless complexity). Known cost: "in N hours" picks made at varying times of day land on neighbouring clock times and take some votes from each other's sets. Counts only shrink by a factor, so nothing is pruned (a set exactly at the target is exempt, so none reaches 0). In simulation a habit moved an hour at old strength 20–30 leads after about 6–7 daily snoozes instead of 16–21, a 30-minute move after 3–4, 15 minutes after 2–3.
- **Decay is exponential with two half-lives** by pattern period, picked from simulation: 21 days for daily/weekly/biweekly patterns, 60 days for calendar-anchored monthly ones (`Dom`/`DomL`/`Mo`). A set spanning both tiers decays at the longer half-life.
- **Custom picker quick times.** The custom picker defaults to today at the strongest quick time still ahead, else the next quarter hour after now (rolling onto tomorrow at 00:00 after 23:45, so Snooze is never disabled on open), and shows up to 4 buttons labeled only by a learned clock time. They come from a separate, date-independent counter per 5-minute clock time (`tod`, 21-day half-life), picked greedily like rows: the strongest, then each remaining one discounted by every pick's weight × 2^(−|Δ| / 30 min), Δ the clock-time distance the short way round midnight (23:50 and 00:15 are 25 minutes apart); up to 4, shown in clock order (5-minute neighbours can still both show when nothing else competes). Each button keeps its undiscounted weight, so the default above is the first pick. A button on date D means D at that clock time, exactly like typing it; it's disabled once past and commits with source `custom`. Every commit feeds it except same-day snoozes and "in N hours" suggestion picks (the commit carries the picked row's key so the engine can tell). A commit that credits a slot also multiplies every other slot's count by 1 − 2^(−d / 30 min), d the same clock distance round midnight; one that credits none touches none. The old named Morning/Evening buttons, Android's saved morning/evening times and its "Set as" button are gone — don't restore them.
- **Web menu and picker layout.** Each menu row is an icon tile, the label without its time (`labelParts`), and the time in its own right-aligned column; the icon comes from `rowIcon`, a port of Android's so both platforms pick the same glyph. Desktop shows it as a popover (flipped upward near the viewport bottom); phones as a bottom sheet headed by the todo's text. "Pick date & time…" swaps in a built-in Sunday-first month calendar (`monthGrid` in `utils/calendar.ts`; past days disabled, identical in every browser), the quick-time chips (tapping one snoozes immediately), and a typed 24-hour time field with Snooze on the same row — no Cancel, and every control in the picker shares one height.
- No cold-start seeds: before any real history, the menu shows only Custom. A key is eligible as soon as its live score is above a small floor (0.05).
- "Last" persists: the most recent custom pick, shown as an extra row while it's in the future and no ranked row lands at exactly the same time. It's named like a ranked row ("Last · Tomorrow morning", "Last · This Friday afternoon", "Last · Next Tuesday morning"), falling back to the date ("Last · Mar 20") only when no phrase fits.
- Picking a ranked suggestion, "Last", a quick time, or Custom all feed the learned counts — every commit is a training signal.
- A pick whose time has already passed is rejected (no todo write, no learning) and the menu stays open; the open menu refreshes its clock every 30 s so stale rows update.
- Undo reverses exactly what that pick changed (the touched set, the touched quick-time slot, the pick count, and every other set and slot it took votes from, each put back as it was): signed in, it adds back the exact amounts the pick added and took, so changes other devices made in between are kept.
- **Pick-rank logging (opt-in), to judge whether 5 rows is the right number.** Ranking runs 20 rows deep (`rankDeep`); the menu shows the first 5 in time order (`shownRows`), unchanged. A deep row's rank is its 1-based position in greedy order; same-time keys take no index. Each commit gets a key (`pickLogKey`): `1`..`20`, the rank of the deep row landing on the target's minute, however it was picked (menu, "Last" or custom picker), or `none`. So a custom pick on a hidden row logs `6`..`20`. The deep list comes from the same stats and `now` the open menu used, before the commit. Lifetime integer counts go in `snoozeVotes.picks`, only while signed in and `users/{uid}.snoozePickLog` is true ("Improve snooze suggestions" switch in the account menu/sheet, signed in only). Turning the switch off deletes `picks`. Each logged pick also bumps that key's field in the shared `snoozePickLog/global` by 1 (undo by -1), as a separate server-side `increment` write so a rejection never costs the user's stats; nothing is written to it while opted out (an undo after opting out included), and opting out leaves existing counts alone. Each logged pick costs one extra Firestore write (free tier: 20k/day), so watch it as users grow.

### Focus Behavior
- No todo should be focused when opening the app
- No todo should be focused when changing filters
- No todo should be focused after a state-changing swipe (complete, reactivate, snooze, delete)
- No todo should be focused when the app is backgrounded
- No todo should be focused after pressing back
- No todo should be focused after the keyboard is dismissed (e.g. swipe down)
- When a todo gains focus, scroll to it first
- No extra space should appear below the search bar when focusing a todo

### Undo
- The undo buffer holds one most-recent action — a delete, a snooze, or a complete. A later action of any kind overwrites the prior buffer (single slot, most-recent-wins)
- The buffer is a tagged entry: web `lastUndo: { kind: "delete" | "snooze" | "complete"; todos }` in the UI reducer; Android a private `UndoableAction` sealed type (`Delete` | `Snooze` | `Complete`) on the ViewModel
- Undo chip auto-expires after 5 seconds; cancelled when changing filters or creating a new todo
- Web shows it as a floating snackbar (`undo-snackbar.tsx`): a pill at the bottom centre (dark in both themes) (above the dock on phones) with the action label, an Undo button, a ⌘Z (Ctrl+Z off Mac) hint on desktop, and a hairline that drains over the 5 seconds. Both platforms label it Completed / Snoozed / Deleted (one todo) / Deleted N todos (several)

#### Delete
- "Clear all done" appears only on the Done filter with a non-empty done list. Web: a "Clear all" text button in the list header (desktop) / app bar (phone), so it never shares a slot with the undo snackbar. Android: a "Clear all" text button in the top bar on the Done filter, next to search
- Tapping it clears focus, deletes all done todos, and shows the "Undo" chip
- A single swipe-delete (DONE row swiped end-to-start) also shows the "Undo" chip at the bottom, on any filter
- The empty-draft blur-cleanup (new todo abandoned without typing) does NOT show the chip — the user never had content to lose
- Tapping "Undo" re-inserts the deleted todo(s) with their original modifiedAt so they land back in their previous sort position (true undo)

#### Snooze
- Committing a snooze (learned suggestion, "Last", quick time, or custom pick) shows the "Undo" chip; tapping it reverts the todo to its pre-snooze snapshot (prior state/snoozeUntil/modifiedAt), so it lands back in its previous sort position
- Snooze undo restores via the normal update path (the row still exists, unlike a delete which re-inserts); `serverModifiedAt` bumps on the write so it passes the server-time rule
- Web: `lastUndo` drives the same chip as delete (label "Snoozed"), and ⌘/Ctrl+Z reverts it. Android: snooze undo shares the delete machinery — `snoozeUndoable` on the ViewModel buffers the pre-snooze snapshot as `UndoableAction.Snooze`, arms the shared undo snackbar, and applies the snooze; tapping Undo re-applies that snapshot through the normal update path
- Snooze undo only surfaces on the filter where the snooze happened (Active/Snoozed); a filter change clears it, so it never competes with "Clear all done" on the Done filter

#### Complete
- Marking a todo done shows the "Undo" chip; tapping it restores the pre-done snapshot (prior state/snoozeUntil/modifiedAt), so it lands back in its previous sort position — mechanically identical to snooze undo (the row still exists, restored via the update path)
- Web: `markDone` buffers `{ kind: "complete" }` (chip label "Completed"); ⌘/Ctrl+Z reverts it. The complete trigger is the left state-icon click. Android: swipe-to-complete (end-to-start on an Active/Snoozed row) routes through `completeUndoable` on the ViewModel, which buffers `UndoableAction.Complete` and raises the shared undo snackbar. Android shows undo as a dark snackbar above the floating filter bar, labeled by the action (`undoLabel` on the ViewModel: Completed / Snoozed / Deleted / Deleted N todos)
- Like snooze undo, it only surfaces on the filter where the complete happened; a filter change clears it

### Sync Indicator (web)
- The sync pill (`sync-pill.tsx`, next to the filter title in the list header / phone app bar) only appears while syncing (Firestore snapshot is `fromCache` — not yet confirmed with the server); a confirmed-synced state shows nothing
- **Delay-show debounce**: `fromCache` blips on/off around writes and metadata changes (`includeMetadataChanges: true`), which flickered the icon. `SyncPill` only surfaces the indicator after `syncing` has been continuously true for `SYNC_INDICATOR_DELAY_MS` (500ms) and hides it immediately when it settles, so transient blips never flash the spinner; only a genuinely slow/offline sync shows it
- While syncing and online: muted pill with a spinning arrow ("Syncing…")
- While syncing and offline (`navigator.onLine === false`): amber pill with a cloud-off icon ("Offline"; tooltip "Offline — changes saved on this device")
- Offline is subordinate to syncing — never shown when `!syncing`, since there's nothing pending to sync
- Online status comes from `useOnlineStatus` (`utils/use-online-status.ts`), a `useSyncExternalStore` hook reading `navigator.onLine` live so online/offline event ordering can't leave a stale value

### Offline & install (web)
- The web app is an installable PWA that opens with no connection. `app/manifest.ts` is the manifest (base-path aware); icons are `public/icon-{192,512}.png` (the favicon glyph on transparent, 85% of the height, light-theme colors) and `app/apple-icon.png` (the same on the page background, since iOS fills transparency with black). No generator script: they were rendered from the `icon.svg` paths with `rsvg-convert`.
- `bun export` runs `scripts/build-sw.ts` after `next build`: it writes `out/sw.js` from `scripts/sw.js`, prepending the list of built files and a version hashed from them. The worker saves every listed file on install (one missing file fails the install, so dotfiles, `.txt` and 404 pages are skipped), serves them cache-first, and answers a navigation with the saved page at that path (pages are saved under their directory URL, so `/privacy/` gets the privacy page), else the app page. Todo data offline is Firestore's persistent cache / localStorage, not the worker.
- Updates never apply silently: a new worker waits, the undo-snackbar slot shows "New version · Reload" with a close button (when no undo is showing; closing hides it until the next new version), and Reload tells it to take over and reloads the page. The page checks for a new version whenever it becomes visible. The worker is only registered in production builds, so `bun dev` is unaffected.
- "Install app" sits in the account menu (`InstallRow` in `auth-menu.tsx`, state in `utils/pwa.tsx`): it opens the browser's install prompt where one exists (Chrome/Edge), shows "Tap Share, then Add to Home Screen" in iOS Safari, and is hidden otherwise or once installed. Sign-in runs through `auth.latr.hafa.cc` (the `authDomain` in `utils/firebase.ts`, a Firebase Hosting custom domain), the same site as the app, so it works from an installed iOS home-screen app, which blocks storage for a sign-in helper on another site.

### Snooze is derived
- **`state` is only `ACTIVE` or `DONE`.** Snoozed-ness is not stored — it is computed from the clock: a todo is snoozed iff it isn't done and `snoozeUntil` is still in the future (web `isSnoozed` in `utils/todo.ts`, Android `Todo.isSnoozed(nowMillis)` in `TodoFilter.kt`). Snoozing writes `snoozeUntil`; nothing writes a state to say "this is snoozed", and **nothing writes anything when a snooze lapses**.
- There is no auto-unsnooze, no `unsnooze()` on the store, no `getExpiredSnoozed`. A lapsed snooze moves its row from Snoozed to Active because `now` advanced, not because a client wrote to it. That makes it correct offline (it's a local computation needing nobody's permission) and impossible to get wrong across devices (there's no write to race).
- Both clients hold a **ticking `now`** that advances at the soonest pending snooze, since no data change will announce the lapse: web keeps it in the store provider (`now` in the context; a `setTimeout` to the next expiry) and every snooze-derived read takes it from there; Android keeps `nowMillis` in `TodoScreenContent` (a `LaunchedEffect` `delay`ing to the next expiry, plus a bump on `ON_RESUME` and on pull-to-refresh) and threads it into `filterAndSort` and each row's `snoozed` flag.
- **Why it was built this way** (do not "restore" the write): the old design flipped `state` to `ACTIVE` on expiry via an automatic Firestore write. Because the Firestore listener's first emission is cache-only, a client with a stale IndexedDB cache would fire that sweep against months-old data on load. The payload sent `serverModifiedAt: <basis> ?? serverTimestamp()`, and the `??` fallback (taken for legacy docs with no basis) resolves to `request.time`, which satisfies the rule's `>=` unconditionally — bypassing the very CAS meant to stop stale writes. It silently overwrote `state` on live docs: todos completed on another device came back as `ACTIVE`, and todos re-snoozed to a future time kept that future `snoozeUntil` while being forced to `ACTIVE` (the minimal payload didn't touch `snoozeUntil`) — which also sorted them above everything, since `activeSortKey` reads `snoozeUntil`. Deriving the state removes the write, and therefore the whole failure class.
- Corrupt rows from that era (`state: "ACTIVE"` with a future `snoozeUntil`) **heal themselves** under the derived rule: they simply read as snoozed until their time passes. No repair migration was needed. Rows whose `DONE` was overwritten are unrecoverable (the state was destroyed) and must be re-completed by hand.

### Sort Order
- Active: by `activeSortKey` (`utils/todo.ts`) — snoozeUntil (unsnoozed, most recently unsnoozed first) else modifiedAt — descending. Every filter's final tie-break is `id` (a stable uuid) so equal-time rows never flip-flop. The **web** sort ignores `pinned` (pinning is a grouping concern, below); **Android** keeps pinned-first in its sort, which also puts the Pinned group first.
- Snoozed: by snooze time ascending
- Done, All: by modifiedAt descending

### Grouping
- The web list renders in buckets whose key is the *same* key the list is sorted by, so a row's bucket and its position can never disagree. (The old modifiedAt-only grouping fought the Active sort: a recently-unsnoozed row sorted at the top but fell into a late date bucket.) `groupForFilter` (`utils/group.ts`) buckets an already-sorted list, preserving order within each bucket.
- Active: a **Pinned** bucket on top (all pinned rows), then date buckets Today / Yesterday / This week / Earlier keyed on `activeSortKey` — so an unsnoozed row buckets by its unsnooze time. Pinned rows appear only in the Pinned bucket.
- Snoozed: Later today / Tomorrow / This week / Later keyed on snoozeUntil.
- Done, All: date buckets keyed on modifiedAt.
- Search: one unlabeled group (relevance-ranked, so date/pinned buckets would be meaningless).
- Android renders the same groups (`ui/TodoGroups.kt`, a port of `group.ts`, unit-tested) as `LazyColumn` header items with the same counts; none while searching.
- Counts (filter title, sidebar/filter bar, group headers) show only when > 0, on both platforms.

### Pinned
- `pinned: boolean` on every todo, synced (web `toFirestoreFields`/`fromFirestore`, Android `toMap`/`fromMap`, Room column already in schema v9). Defaults to false.
- Pinning only floats items to the top of the **Active** list; Snoozed (snooze-time order) and Done/All (modifiedAt order) ignore `pinned` so a time-ordered view isn't reshuffled. But a **snoozed** todo can still be pinned — it just doesn't float until it unsnoozes and enters Active. The affordance is therefore shown on every row *except* a done one (web `showPin = !isDone`; Android passes `onTogglePin = null` only when `state == DONE`).
- It's a toggle: the web hover button and the Android long-press read the current `pinned` and flip it (web label "Unpin" when already pinned).
- Toggling always **bumps** `modifiedAt` (web `Date.now()`, Android `touchModifiedAt = true`) — a pin is an edit. On an **active** row it additionally **clears the was-snoozed marker** (`snoozeUntil = null`) so the toggled row becomes a plain recent row and lands at the top of its group rather than snapping back to its old unsnooze-time position. A **snoozed** row keeps its snooze time, so the bump doesn't move it (Snoozed orders by `snoozeUntil`); on Done/All, which order by `modifiedAt`, the bump does float the row — accepted, it was just edited. Web centralizes both cases in `withPinToggled` (`utils/todo.ts`, unit-tested); Android inlines the same branch at the `onTogglePin` call site. Pin never arms or clears the undo buffer.
- **State icon beats pin icon, but the pin keeps its colour.** The left icon shows the pin *glyph* only on a row that is genuinely active — precedence is done → snoozed → pinned → was-unsnoozed → plain — since that's the only row whose order the pin changes. A pinned done or snoozed row keeps its own glyph (check / filled clock) but is drawn in the **pin tint** (web `text-accent`, Android `colorScheme.primary`), so pinned-ness is still legible everywhere without the glyph lying about the row's state. On Android a done row is already `primary`-tinted, so a pinned done row looks unchanged there; the snoozed one goes tertiary → primary. The icon's "Pinned" `contentDescription` follows the tint, not the glyph.
- No scroll-into-view on toggle (deliberately removed). The `modifiedAt` bump already lands the row near the top of its group — a pinned row at the very top, an unpinned row just below the pinned rows — so it stays visible in the common case (toggling while at the top of the list). Chasing the row with a programmatic scroll wasn't worth the complexity: the row's `animateItem` reorder is mid-flight for a few hundred ms after the toggle, so any visibility check reads stale offsets, which forced a fixed settle delay and still misfired. The list just re-sorts (with its row animation) and the viewport stays put.
- Web: a pinned active row is identified by its **left/primary icon** — an outlined pin (`LuPin`, accent) in place of the state ring. Clicking it still marks done, exactly like the `wasUnsnoozed` outline-clock icon does — the pin is a state *indicator*, not the toggle. Pinning is the **hover pin button** on desktop (between snooze and delete in the action cluster, `showPin`, `LuPin`), which behaves like every other hover action (hidden at rest, fades in on hover via the shared `hoverAction` class; accent tint when pinned). On phones it's the Pin/Unpin button in the focused row's action strip.
- Android: pin is a **long-press anywhere on the row** (`onTogglePin` on `TodoItem`; the `onLongClick` of the same `Modifier.combinedClickable` that handles tap-to-edit, so it fires over the icon/padding *and* the text). There is **no trailing pin button** — the earlier always-visible button was too much visual noise. A pinned active row is identified by its **left icon**: a primary-tinted outline `PushPin` replaces the state dot. Long-press gives haptic feedback and is a no-op on a done row. Trade-off vs the old button: lower discoverability and weaker TalkBack affordance (the icon carries a "Pinned" contentDescription, but the toggle isn't a discrete a11y action). The swipe gestures are unchanged (`SwipeToDismissBox`: complete/delete + snooze/reactivate); there is no tap-to-complete on the left icon, so rows also expose Complete/Snooze/Delete (or Restore) as TalkBack custom actions. Snoozed and was-snoozed rows use a clock icon (`Schedule`, outlined for was-snoozed), not a bell; a was-snoozed row's second line reads "Unsnoozed · HH:mm".

### Inline styles
- `*bold*` and `_italic_` render in todo text on both platforms: at rest, while editing, in the web compose row, and in the snooze sheet header (not in the search field). The markers stay in the text and are shown dimmed; nothing new is stored, so older clients just show the raw markers.
- One parser per platform (web `utils/inline-style.ts`, Android `util/InlineStyle.kt`), both run against `testdata/inline-style-fixtures.json`. A marker opens only when followed by non-whitespace and not preceded by a letter/digit, and closes only when preceded by non-whitespace and not followed by a letter/digit, so `snake_case`, `2*3*4` and `a * b` stay literal. "Letter/digit" is Unicode letters, decimal digits and combining marks (so a decomposed `é` doesn't end a word); "whitespace" is exactly U+0009–000D, 0020, 0085, 00A0, 1680, 2000–200A, 2028, 2029, 202F, 205F, 3000 and FEFF, on both platforms. Runs of the same marker (`**x**`, `__init__`) are literal, spans never cross a newline, unclosed openers are literal, and closing an outer span drops any crossed inner opener. Spans nest (`*_x_*`).
- Search matches against the text with span markers removed (`plainText` / `InlineStyle.plain`), so "milk" finds `_milk_`.
- Web: ⌘B / ⌘I (Ctrl on other platforms) wrap the selection (trimmed of surrounding whitespace) in `*` / `_`, unwrap it if it's already wrapped in that marker, or insert a pair with the caret between, as CodeMirror transactions, so ⌘Z undoes them. Matching is linear-time (per-marker open lists), since the parse runs on every keystroke.

### Fast Todo Compose Loop
- Adding a todo moves to the Active filter/pane *and* clears the search query, so the new row is always visible (Android FAB, web compose row submit)
- When in fast compose mode with an empty todo, pressing Done should clear focus and delete the empty todo
- IME action should be "Done" when the todo text is empty (not "Next")
- IME action should be "Next" when the todo text is not empty (creates new todo)

## Firestore schema

`users/{uid}/todos/{todoId}` — each doc: `{ text, state: "ACTIVE"|"DONE", createdAt, modifiedAt, snoozeUntil, pinned }`. Rules in `firebase/firestore.rules` restrict reads and writes to the owning `uid`.

There is no `SNOOZED` state — see [Snooze is derived](#snooze-is-derived). Docs written by older clients still carry one; both clients map it to `ACTIVE` on read (web `readState` in `utils/todo.ts`, Android `Todo.readState`, and the Room `Converters.toTodoState`, which must not use `valueOf`), so `snoozeUntil` alone decides.

`users/{uid}` (the parent doc itself, not a todo) additionally holds `snoozeVotes`: the account's learned snooze-suggestion counts, one set shared by every device (`sets: {<setId>: n}`, `tod: {<HHMM>: n}`, `lastCustom: {target, at} | null`, `picks: {<1..20|none>: n}` lifetime counts, `folded: {<deviceId>: true}` — see [Snooze Options](#snooze-options-learned-suggestions)). Each `n` is a plain number saved **scaled**: a vote cast at time `at` adds 2^((at − `VOTE_EPOCH`) / half-life) instead of 1 (`VOTE_EPOCH` is 2026-01-01 UTC; half-life 21 or 60 days by set, 21 for `tod`), and the live count is `n` × 2^(−(now − `VOTE_EPOCH`) / half-life). Old votes fade because new ones are bigger, so no time is saved per count and every change is a server-side `increment` (a vote adds, taking votes adds a negative amount, undo adds the opposite): it works offline, needs no transaction, and never overwrites another device's change. Readers hand the engine each count as `{c: n, t: VOTE_EPOCH}` (`sharedFromWire`), so the engine is unchanged; a commit's or undo's amounts are the scaled difference between the engine's before and after (`voteDeltas`). Readers drop counts at or below 0, malformed entries and anything not matching the key format. A double holds this until about 2085 (1,024 doublings of 21 days); there is no reset. Signed out, a device keeps its own counts locally in the old `{c, t}` form (web localStorage, Android Room); signing in adds them to the account's once and clears them, and they aren't used while signed in. The same doc holds `snoozePickLog: boolean` (missing = false), the per-user opt-in for `picks`. No rules change was needed — `match /users/{userId} { allow read, write }` already covers the whole document, not just the `todos` subcollection. Deleting the account also deletes this parent doc; `todos` live in a separate subcollection and are unaffected.

Older builds saved one block per device at `snoozeStats.<deviceId>` (`{v, sets: {<setId>: {c, t}}, tod, lastCustom, picks}`), each device replacing its own block whole and readers summing them; taking votes only reached the committing device's block, so a time with votes on another device kept its row. A current build, on seeing a block whose id isn't in `snoozeVotes.folded`, runs one transaction that adds every such block to the shared counts, marks the ids in `folded` and deletes `snoozeStats` (`foldBlocks`; a transaction so two devices can't both add a block). A device still on an old build keeps saving its block; it is already in `folded`, so current builds ignore it, and what that device learns is lost until it updates (when its local copy is dropped, being that same block).

`snoozePickLog/global` is one shared tally: an integer field per pick key (21 keys), summed over every opted-in user. Only admins can read it (Firebase Auth custom claim `admin: true`, checked as `request.auth.token.admin`); no client can delete it; a signed-in user's write must change exactly one valid pick-key field by ±1 (starting from 0). Each write also sets `key` to the name of the field it bumps, because rules can't pull the changed field's name out of `affectedKeys()`; the rule checks `key` against the pattern and requires the changed fields to be only `key` and the field it names.

### Android release

`.github/workflows/cut-android.yml` (run by hand, choosing patch/minor/major) runs the build checks, bumps `versionName` and `versionCode` in `android/app/build.gradle.kts` on `main`, tags `android-vX.Y.Z`, uploads the signed bundle to Play's **internal testing** track with Gradle Play Publisher (`./gradlew :app:publishReleaseBundle`, the `play {}` block in the app build file), and creates a GitHub release. Promote to production in the Play Console. The GitHub release is made with the workflow's token, so it does not trigger the web deploy.

One-time setup, in this order (Play only takes uploads from the workflow once the app exists and has one bundle):

```properties

keyAlias=upload

```

3. `cd android && ./gradlew bundleRelease`, then create the app in the Play Console and upload `app/build/outputs/bundle/release/app-release.aab` to internal testing by hand. This first upload uses `versionCode` 1; the workflow bumps it from there.
4. Copy the SHA-1 and SHA-256 from Play Console → Setup → App signing into the Firebase project's Android app, or Google sign-in fails in the Play build.
5. In Google Cloud (project `hafaio-latr`) enable the Google Play Android Developer API, create a service account and download a JSON key for it to `android/play-service-account.json` (git-ignored). In Play Console → Users and permissions, invite the service account's email with permission to release to testing tracks for this app.
6. Copy the same key, passwords and files into a GitHub environment named `release` (the workflow's `publish` job reads them from there), from the repo root:

```sh
gh api -X PUT repos/hafacc/latr/environments/release
base64 -i android/latr-upload.jks | gh secret set ANDROID_KEYSTORE --env release
gh secret set ANDROID_KEYSTORE_PASSWORD --env release   # prompts
```

The key, `keystore.properties`, `play-service-account.json` and `google-services.json` exist only on this machine and in GitHub's secrets, which can't be read back, so back them up. If the key is lost, Play can reset the upload key on request (Play holds the real signing key).

## Design decisions

- **Android theme: the phone's wallpaper colors, no overrides.** `minSdk` 34 means dynamic color is always available; snooze = `tertiary`, done = `primary`, delete = `error`, restore = `secondary`. `theme/Color.kt` holds latr's own palette, used only when dynamic color is off (previews). Geist is bundled as a variable font (`res/font/geist.ttf`, OFL in `assets/licenses/`), no downloadable-fonts dependency. The night window theme is dark (`values-night/themes.xml`, background `system_background_dark`); a light one shows through as white flashes at launch, around the keyboard, and in the text selection toolbar.
- **Android layout: top bar, floating filter bar, one-step snooze sheet.** Title and count, search that opens in place, and account in the top bar; a floating filter bar (the selected filter shows its label) plus the add button at the bottom, with `filterSwipe` paging kept. Swipe backgrounds are soft container colors that switch to full strength with a haptic tick past the threshold. The snooze sheet's custom flow is one `ModalBottomSheet` stepping menu → date → time.
- **No Zustand on web.** A `useReducer` + context provider is ~60 lines and handles everything the todo store needs. Pattern: `utils/store.tsx`.
- **Tailwind v4 semantic tokens.** Colors live as `--color-*` CSS variables inside `@theme` (light) with `.dark` overrides. Components use utility classes like `bg-surface`, `text-muted` — no `bg-[#hex]` anywhere. The palette ("quiet paper, one ink") is a warm off-white/near-black pair with one latr blue accent, plus soft container fills for the two semantic hues (`snooze`/`snooze-soft` amber, `done`/`done-soft` green) and `danger-soft`; `text-secondary` sits between `text` and `muted`. Elevation is flat except floating layers (`shadow-pop` popovers, `shadow-dock` dock/snackbar, `shadow-sheet` sheets), which in dark mode add a 1px border ring since shadows vanish there.
- **Web type and icons.** Geist via `next/font/google` (`--font-geist`, feeding `--font-sans`); times use `tabular-nums` so they line up. Icons are Lucide through `react-icons/lu` only (no FontAwesome/Bootstrap mix), and snooze is a clock everywhere.
- **Web is responsive, not a separate mobile site.** Below `md` (768px) the sidebar and list header give way to an Android-style shell: a sticky app bar (title, count, sync pill, search icon that swaps in a search field, avatar → account sheet), a fixed bottom dock (filter pill toolbar in Android's Snoozed/Active/Done/All order, the selected one expanded with its label, plus a FAB), and native `<dialog>` bottom sheets (`sheet.tsx`) for snooze and account. Desktop keeps the hover-collapse sidebar (now with Active/Snoozed counts and an account row whose popover holds a System/Light/Dark segmented control). The FAB switches to Active, clears search and calls `focus()` synchronously on a compose editor that stays mounted (collapsed to zero height on phones) — iOS only raises the keyboard for a focus inside the tap handler. `useMediaQuery` (`utils/use-media.ts`) picks popover vs. sheet and hover cluster vs. action strip.
- **Firestore snapshot listener is the sole source of truth when signed in.** `FirestoreTodoStore` reads/writes straight through Firestore (with `persistentLocalCache`); its `onSnapshot` listener is the only thing that populates the UI, so there's no separate local store to reconcile and an echo of our own write coming back through the listener can't clobber in-flight typing. Cross-device write conflicts resolve via the server-time gate (below), **not** a `modifiedAt>` comparison — so clock skew between Android (`System.currentTimeMillis()`) and web (`Date.now()`) can't silently drop edits.
- **The snapshot listener self-heals with backoff.** A Firestore listener that delivers an *error* (not a transient drop, which the SDK reconnects silently) is dead for good. Both clients re-register with capped exponential backoff (1s→30s): Android propagates the error out of the `observeAll` `callbackFlow` (`close(err)`) and wraps it in `retryWhen`; web re-`attach`es on a `setTimeout` from the `onSnapshot` error callback. Recovery needs no user gesture. Both reset the backoff after a healthy emission (web on a server-confirmed snapshot; Android via an `onEach` that zeroes its failure counter). Web additionally exposes `reattach()` (fired on tab-wake / online) as an immediate-retry-that-resets-backoff; Android relies on `retryWhen` plus `WhileSubscribed` re-collecting the flow (a fresh listener) once its 5s grace lapses after the last subscriber leaves. The `snoozeStats` doc listener (both platforms) follows the same capped-backoff-and-reset pattern, implemented imperatively (a plain retry `setTimeout`/`Job` rather than `attach`/`retryWhen`) since it isn't collection-based like the todo listener.
- **Store swaps live in `TodoStoreHolder`; the auth listener only swaps.** `onAuthStateChanged` swaps the live `TodoStore` (local ↔ Firestore) and does nothing else. Moving data happens only on the explicit user-initiated entry points `signIn` / `signOut` / `deleteAccount`. On sign-in, `mergeLocalIntoFirestore` (web) / `mergeRoomIntoFirestore` (Android) `getDocs` the full remote collection, pushes local rows that are newer (`modifiedAt >` remote) or absent remotely, and drops local rows matching a remote tombstone (so a delete made on another device isn't resurrected) — then the auth listener swaps.
- **Todos live in one place: the device while signed out, the account while signed in.** Sign-in *moves* the device's todos into the account: once the merge's push succeeds the local store is emptied (a failed merge leaves it, so signing out and in retries). Sign-out leaves nothing of the account on the device: it waits up to 3 s for unsent writes (`waitForPendingWrites`); if they haven't gone it changes nothing and the UI asks ("Changes haven't synced": Wait / Sign out now), and a forced sign-out drops them. It then signs out, ends the Firestore instance and clears its on-device cache (`clearDbCache` on web; `terminate` + `clearPersistence` on Android), so the next sign-in starts a fresh instance. Delete account asks "Keep todos on this device" or "Delete everything": keep copies the account's todos onto the device before the remote wipe (they are matched by id, so the copy is harmless if the delete then fails) and its snooze counts only after the account is gone (web `keepLocally`, Android `keepCounts`; counts add up, so a copy left by a failed delete would be added to the account twice on the next sign-in; they are stored in the shared `{c: n, t: VOTE_EPOCH}` form, which the sign-in push adds back unchanged); delete everything empties the device too. So the app works with sign-ups closed, or built with no sign-in at all. Builds before this kept a copy on the device while signed in; it is dropped once, the first time a build with this change starts signed in (web `latr:local-moved:v1`, Android a `user_prefs` flag).
- **The logo is the clock-hands L with a darker copy behind it, offset 2.2 down-right** on the 108×108 canvas (solid, no blur). Web: front `accent` over `accent-shadow` (`#2f6fde`/`#163a7d` light, `#74a4f5`/`#2f6fde` dark); `app/icon.svg` switches pairs with a `prefers-color-scheme` query, since the light pair's navy vanishes on a dark tab bar. `Logo` (`components/logo.tsx`) always draws the copy, filled by `shadowClassName` (default `fill-accent-shadow`); the empty-list watermark is `border` over `border-strong` (`#e8e6e2`/`#c8c5be` light, `#2e2c2a`/`#45423f` dark, where a darker copy would vanish into the page). Android: the launcher icon is the L alone in one color (`ic_launcher_foreground.xml`, `system_accent1_600`, night `_200`; themed `ic_launcher_monochrome.xml`), since home screens draw icons in a single color. Only the splash screen keeps the copy: `ic_splash.xml`, set as `windowSplashScreenAnimatedIcon`, has it as a second path, `system_accent1_800` behind `_600` (night: `_500` behind `_200`); the light theme sets `windowSplashScreenIconBackgroundColor` to the launcher background (`system_accent2_100`), which the night splash background already matches.
- **Favicon viewBox cropped to `49 27 24 34`**. The L reads at 16×16; the full 108×108 Android composition is illegible at that size.
- **Left icon = primary state flip; right cluster = secondary actions.** Click the left icon on any row to toggle its main state (active↔done, snoozed→active). Right actions fade in on hover and vary by state.
- **Web text editing is CodeMirror 6, so inline styles render in real bold.** Direct deps: `@codemirror/state`, `@codemirror/view`, `@codemirror/commands` (which pulls in `@codemirror/language` and `@lezer/*`); about 85KB gzipped, loaded up front. Keys are `standardKeymap` + history only (no indent or bracket commands); Shift+Enter is a plain newline in rows. `TextEditor` (`components/text-editor.tsx`) is a plain-text CodeMirror view: the document is the todo text with its markers, and `*bold*`/`_italic_` are `Decoration.mark`s recomputed from `utils/inline-style.ts` on every change (`.md-bold` is `font-weight: 600`, matching Android SemiBold). CodeMirror owns caret, IME/composition, undo history, plain-text paste and wrapping. Todo rows render static `StyledText` at rest (cheap for long lists; same classes as the editor, so nothing shifts) and mount an editor only while the row is focused. The static text's `mousedown` is prevented and opens the editor with the caret at the pointer (`posAtCoords`), since a native focus would land on the node being replaced; a drag started there extends the new editor's selection by hand; keyboard focus opens it with the caret at the end. The compose row is one always-mounted, single-line editor so the FAB and `n` can focus it synchronously (iOS); typed/pasted newlines become spaces and Enter submits. ⌘B/⌘I are CodeMirror commands built on the pure `wrapSelection`, so they undo with ⌘Z. ⌘Z while the undo chip is showing still reverts the last todo action (page capture listener) instead of editor history. Dev StrictMode remounts an editor right after focusing it; `TextEditor` carries the focus and caret across. Rejected: a transparent textarea over a styled copy (it needed faux bold, because Geist widens with weight), a hand-rolled contenteditable (caret restore, IME, undo), and full rich-text editors (Lexical/Tiptap/Slate store formatting, not markers).
- **Android rows render display text at rest, swapping to an editor on tap.** Each `TodoItem` shows a plain `Text` until tapped, then swaps to a `BasicTextField` (`editing` gates the two). This keeps scroll cheap (a `BasicTextField` per visible row is a real composition cost) and frees the row for a long-press-to-pin gesture that an always-present editor would swallow as text selection. Seamlessness depends on the display `Text` and the field sharing one `TextStyle` with no padding on either, so the swap doesn't shift a pixel. Tap-to-edit and long-press-to-pin are a single `Modifier.combinedClickable` on the whole row (**not** a raw `detectTapGestures` — nested inside the `SwipeToDismissBox` drag + `LazyColumn` scroll, a raw tap detector dropped most taps). `combinedClickable` gives no tap position, so a passive `pointerInput` on the display `Text` peeks at each down (Initial pass, non-consuming, so it doesn't disturb the click) and records the caret offset via `getOffsetForPosition`; `onClick` opens the editor there, falling back to end for taps off the text. Focus is requested after a `withFrameNanos` delay so it isn't lost when stealing focus from another row's field. Web does the same split (static styled text at rest, a CodeMirror editor while focused; see above), and its pin uses a hover button, not long-press. Both the display `Text` and the editor build their text from one `AnnotatedString` builder (`ui/InlineStyleText.kt`); the editor applies it as a `VisualTransformation` with identity offsets, since the markers stay in the text.
- **Android list scroll perf: cache window + stability config.** All four `rememberLazyListState`s get a `LazyLayoutCacheWindow(ahead = 300.dp, behind = 150.dp)` (experimental foundation API) so heavy rows pre-compose in idle frame time instead of on viewport entry during a fling. `app/compose_stability.conf` declares `com.google.firebase.Timestamp` stable (it's deeply immutable) — without it `Todo.serverModifiedAt` made the whole `Todo` class unstable, so every Firestore echo recomposed all visible rows.
- **Release runs R8, with keep rules for what it can't see.** `isMinifyEnabled`/`isShrinkResources` are on for release (judge scroll smoothness on a release install — debug Compose is expected to jank); release is signed with the upload key when `storeFile`, `storePassword`, `keyAlias` and `keyPassword` are set in the git-ignored `android/keystore.properties` (CI passes them as `-Platr.<name>`; `bundleRelease` then gives the `.aab` for Play), and debug-signed otherwise so `installRelease` still works. Two things R8 can't statically see and would strip: Credential Manager's Play Services provider, loaded via `Class.forName` from manifest metadata (kept via `proguard-rules.pro`, verbatim from the Credential Manager docs) — without it `getCredential()` fails and Google sign-in silently does nothing; and `default_web_client_id`, read only through `resources.getIdentifier` so the resource shrinker can't see it (kept via `res/raw/keep.xml`) — without it release builds disable auth entirely.
- **Android backup leaves out Firestore's offline cache** (`backup_rules.xml`, `data_extraction_rules.xml`, file name hard-coded with the project id): a restored cache could replay old unsent writes. The Room database (signed-out todos) is backed up.
- **Web sends a Content-Security-Policy as a meta tag** (`CONTENT_SECURITY_POLICY` in `app/layout.tsx`, production builds only; dev needs eval). GitHub Pages can't send headers, so `frame-ancestors` isn't available. It allows scripts from the site and `apis.google.com` (Firebase sign-in loads it), connections to `*.googleapis.com` and `auth.latr.hafa.cc`, the sign-in frame from `auth.latr.hafa.cc`, and avatars from `*.googleusercontent.com`. `'unsafe-inline'` scripts stay because the static export emits inline ones. A new external host (fonts, analytics, another Firebase product) must be added here or it is blocked silently.
- **No `.env.local`.** Firebase web-config values ship in the client bundle by design; there is no secret. Inlined in `web/utils/firebase.ts` so a fresh clone builds without env setup.
- **Deletes are tombstones, and the query hides them.** A delete writes `{deleted: true, text: "", modifiedAt, serverModifiedAt}` (the text is blanked so deleted content isn't kept; undo holds the full todo and rewrites every field) (web `updateDoc`, Android `.update()` — *not* `set`/merge, so a doc already deleted elsewhere isn't re-created as a tombstone) instead of removing the doc. The point is the sign-in merge: with a hard delete, "absent remotely" is ambiguous — *never synced* or *deleted on another device*? — and the merge guessed "never synced" and pushed the row back up, resurrecting every delete. A tombstone removes the guess.
  - The tombstone write is **`set`/merge, not `update`** — `update` rejects a missing doc, so one NOT_FOUND (a row an older, hard-deleting client removed) would abort the whole `clearAllDone` batch and clear nothing. `set`/merge keeps the batch atomic *and* works offline (a transaction would give atomicity too, but Firestore transactions need a server round trip and fail offline). If the doc is gone, `set`/merge just re-creates it as a bare `{deleted: true}` gravestone: invisible behind the `deleted == false` query, read as "deleted" by the merge, and it usefully converts an old client's hard delete into a real tombstone.
  - The cost of keeping them is paid **server-side**: both listeners query `where("deleted", "==", false)` (web `LIVE_ONLY`, Android `liveOnly`), so a tombstone never reaches a client — no read, no bandwidth, no in-memory filter needed (the `!t.deleted` filters are kept only as a backstop). A tombstoned doc simply leaves the query and Firestore delivers REMOVED, exactly as a hard delete did. Growth is storage-only, and storage is free at this size.
  - **`== false` does not match a doc missing the field**, so every doc must have it. All 151 existing docs were backfilled (2026-07-12; one predated the field — created 2026-04-12, before `deleted` was added in `6325632`, and never rewritten since because it was snoozed a year out). Every write path stamps `deleted`, so new docs are fine. If you ever add a write that doesn't go through `toFirestoreFields`/`toMap`, it must still set it or the todo will vanish from the app.
  - **Local (signed-out) deletes are tombstones too**, and the merge consumes them: `RoomTodoStore`/`LocalTodoStore` mark the row rather than dropping it, the merge pushes it up, then empties the local store (`dao.deleteAll()`, web `clear`). Without that, a delete made while signed out is forgotten and the live remote doc resurfaces on the next sign-in. Reads filter them (`getAllTodos` has `WHERE deleted = 0`; web `getTodos()` holds only live rows, with `getWithTombstones()` for the merge).
  - Hard deletes survive in exactly two places, both correct: the delete-account wipe, and the abandoned-empty-draft cleanup (a todo that never had content isn't worth a tombstone).
  - The merge decision is a pure function — `planMerge` (`web/utils/merge.ts`, `data/TodoMerge.kt`), unit-tested on both platforms. Note it never deletes a *remote* row that's merely absent locally: a fresh device with an empty store must not wipe the account.
  - Undo holds the full `Todo[]` (web `lastUndo.todos`, Android `UndoableAction.Delete.todos`) and restores by flipping `deleted` back to false, preserving the original `modifiedAt` so the row lands back in its prior sort position. Since the doc still exists, that's now a plain update rather than a re-create through the laxer `create` rule.
- **Server-time gated writes via Firestore rule.** Every doc carries `serverModifiedAt = serverTimestamp()` and the rule on `users/{uid}/todos/{id}` requires `request.resource.data.serverModifiedAt >= resource.data.serverModifiedAt`. It's a compare-and-swap on a per-doc version stamp. Every write we make now is a *user edit*, which stamps `serverTimestamp()` (= `request.time`) and so always passes — the rule's remaining job is to reject a write whose basis is stale, which today can only happen to a client whose cache is behind. `serverModifiedAt` is carried as the raw SDK `Timestamp` (web `firebase/firestore` Timestamp, Android `com.google.firebase.Timestamp`) — truncating to millis would defeat the `>=` check even with no conflict.
  - **Never forge a basis.** The one write that used to re-send a basis (the auto-unsnooze) fell back to `serverTimestamp()` when the local `serverModifiedAt` was null, which resolves to `request.time` and passes the CAS *unconditionally* — a stale client then won every race. That corrupted live data (see [Snooze is derived](#snooze-is-derived)) and the write is gone. If a future automatic (non-user-initiated) write is ever added, it must either carry a real basis or not be sent; and it must not run off a cache-only snapshot (web's listener emits `fromCache: true` first).
  - If you need an automatic cross-device write, prefer a **server-side field transform** (`arrayUnion` / `arrayRemove` / `increment`) over a read-modify-write: transforms are evaluated on the server against the current doc, so they're immune to a stale local snapshot and need no CAS at all.
- **Snooze counts are one shared set per account, changed only by adding.** They used to be a block per device, replaced whole by its one writer and summed by readers. That let a device take votes only from its own block, so a time kept its menu row on the strength of another device's votes however often it was snoozed away from. A single set written whole would need a transaction (no offline) or lose concurrent writes; saving each count scaled by vote time makes every change an `increment`, which neither needs. Cost: two devices taking votes at the same moment each take a share of what they last saw, so slightly too much can come off (a count below 0 reads as none).
- **Snooze suggestions store observed pattern combinations, not per-pattern probabilities.** An earlier design split each commit's credit across every pattern it matched and used a simulated "structural overlap" model to discount likely-duplicate patterns at read time. It was replaced: the *exact set* of patterns one commit matches gets one undivided decayed count, and ranking greedily picks the top-scoring pattern, then retires every stored set containing it before ranking the next slot. This uses real observed co-occurrence instead of an idealized calendar simulation, needs no overlap model, and makes a pattern's support fade in lockstep with whatever habit was actually backing it — for free, from the aggregation, not a separate rule. See [Snooze Options](#snooze-options-learned-suggestions).

## Known limitations

- Inline styles can't start or end between two letters, so they don't apply mid-sentence in scripts without spaces (`我*喜欢*你` stays plain). By design: the same rule keeps `snake_case` and `2*3*4` literal.
- Simultaneous edits on web and Android to the same todo resolve by "last write to Firestore wins on next snapshot." This is not true collaborative editing. A client acting on a **stale view** (e.g. a rarely-opened origin whose Firestore cache is far behind) can therefore clobber newer remote state — but only for a write the user actually initiated, at `request.time`. No write happens on its own any more.
- A web sign-out reaches every open tab through the auth listener, and each one re-reads the saved todos, ends its Firestore instance and clears the cache. A tab's clear fails (logged) while another tab still holds the cache open; the tab holding it clears it when its own turn comes.
- Snoozed-ness is derived from **local** wall-clock time, so a device with a badly skewed clock will disagree about which todos are snoozed. Nothing is written, so it self-corrects the moment the clock does.
- A concurrent snooze from two devices resolves LWW on `snoozeUntil` rather than merging (an add/remove set of snooze tokens would merge; see [Snooze is derived](#snooze-is-derived)).
- Undo of a snooze/complete/delete resolves against a concurrent remote edit by the same last-write-wins as any other write. It can no longer *resurrect* a todo deleted on another device, though: deletes are tombstones, so the doc is still there and undo is an ordinary update rather than a re-create.
- Mobile web swipe and the focused-row action strip were only exercised in desktop Chrome's touch emulation, not on real iOS/Android browsers.
- Web row swipes match Android's mapping (start-to-end snoozes, or restores a done/snoozed row; end-to-start completes, or deletes a done row) with guards against Android's over-sensitivity: the gesture is only claimed once `|dx| > 2|dy|`, commits on distance alone (96px or 35% of the row, never velocity), ignores touches starting within 24px of either screen edge (the browser's back swipe), suppresses the tap-to-edit focus once claimed, and never starts from a row that's already being edited, so caret drags stay caret drags (`utils/swipe.ts`, unit-tested). Rows keep pinch-zoom (`touch-pan-y touch-pinch-zoom`). There's no swipe between filters on web — it would fight row swipes and the edge back gesture.
- On first load the web store hydrates from `localStorage` in a mount effect, so there's a brief frame where the todo list is empty before cache loads.
- Tombstones written before deletes blanked the text still hold it, until the account is deleted.
- Tombstones accumulate in Firestore forever (no GC). They cost the clients nothing — the `deleted == false` listener query never fetches them — so this is storage-only growth. Deliberately **no automatic sweep to reap them**: an automatic cross-device write is the exact shape of the bug in [Snooze is derived](#snooze-is-derived). If it ever matters, GC with an admin script.
- Learned snooze-suggestion counts (`users/{uid}.snoozeVotes`) are never pruned; cost is storage-only and small (one number per distinct set and quick time).
- Android excludes its snooze identity prefs from cloud backup and device transfer; a restore without them clears the Room counts, so a restored or new phone never adds another phone's signed-out counts to an account.
- Taking votes uses the counts the device last saw, so a device that was offline, or two snoozing at once, can take slightly too much or too little.
- Signed out, web tabs share one copy of the counts through localStorage (re-read before each commit, plus a `storage` listener); two tabs committing in the same millisecond can still lose one.
- Deploy order matters: a client still on an older build **hard-deletes**, writing no tombstone, so the merge protection is only real once both clients are updated.
